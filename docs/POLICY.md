# Политика выполнения: запрет незаметного GPU→CPU fallback

Принцип 5 базовой документации. Здесь — формализация, пригодная для проверки.

## Правила

P1. Режим по умолчанию — `gpu-strict`. Если ни один GPU-бэкенд (ROCm/HIP или
    Vulkan) не прошёл probe со статусом PASS, запуск модели **запрещён**.
    Система выдаёт ошибку с диагнозом, а не начинает генерацию на CPU.

P2. Явный override возможен только так:
    `lm run --allow-cpu-fallback ...` (флаг печатает предупреждение и пишет
    событие в лог). Молчаливый fallback недопустим ни в CLI, ни в GUI,
    ни в systemd-юнитах.

P3. Во время генерации health-check фиксирует факт использования GPU
    (DRM render activity / ROCm SMI utilization). Если процесс объявлен
    «GPU», но GPU простаивает, а CPU загружен — нарушение P1, задача
    останавливается.

P4. Статусы совместимости: `PASS` (есть machine-отчёт с реального железа),
    `FAIL` (проверено — не работает), `NOT_TESTED` (нет данных).
    Заявления в документации допускаются только для `PASS`.

P5. Любое изменение whitelist GPU или порогов требует нового golden-отчёта
    в tests/golden/ (иначе CI падает).

## Реализация (план E7)

- `localmind-doctor` собирает состояние → JSON → сравнение с ожиданиями.
- Интеграционный тест: эмуляция исчезновения /dev/kfd и /dev/dri/renderD*
  → ожидаемый ненулевой код выхода и сообщение, НЕ запуск на CPU.
